# Core restore adapter

Implemented an offline staging-only adapter. No process launch, source database mutation, historical JSONL rewriting, or raw binary string replacement occurs.

Final schema gate supersedes the earlier broad table-only description below: the adapter now requires the exact SHA-256 fingerprint of all non-internal sqlite_schema definitions (tables, columns, indexes and triggers), user_version 0, and the exact ordered migration version/checksum/success fingerprint. Baseline metadata was read from local state_5.sqlite using read-only immutable SQLite on 2026-09-11, with no user rows inspected. The schema has 42 non-internal definitions and 54 migrations. Its five known timestamp triggers are permitted only as part of that exact fingerprint; altered or extra triggers reject. New columns, changed migration checksums and versions, and a plausible but incomplete threads table all reject before adaptation. Fixtures contain schema definitions and migration metadata only, with newly invented synthetic thread records. Twelve adapter tests plus three Core integration tests pass. This is an observed source structure baseline, not destination application compatibility validation.

Supported state: `state_5.sqlite` with the explicitly enumerated known tables and TEXT `threads.cwd` / `threads.rollout_path`; recognized `project_roots.path` or `root_path`. Unknown tables, views, triggers, missing required path columns, and reserved quarantine collisions reject adaptation. Old `agent_jobs` / `agent_job_items` databases are intentionally rejected. Schema support is conservative and is not a promise of forward compatibility.

SQLite opens only the staging copy, runs quick_check, consumes the copied WAL through SQLite, applies bound-value path changes, removes dynamic tools / remote control / imported external-agent integration records, disables daybreak where present, and checkpoints WAL before closing. The caller must stage every file and preserve the untouched verified package and rollback copy before calling. Do not call this API directly on live data.

Unknown top-level resources, config, auth, skills, plugins, automations, nested sqlite databases, sandbox and process resources move into `.codex-backup-disabled`. The passive allowlist retains sessions, archived sessions, session/history indexes, top-level known history database, and memories. Global state keeps only recognized workspace-root arrays and labels; its complete original is retained disabled. Vault pointer remapping uses UTF-8. Paths match the longest configured prefix at a directory boundary; unmatched values remain unchanged with a warning. Agent identity paths and historical messages remain unchanged. Re-login and explicit integration review are required.

Validation: tests were written before implementation and initially failed because the adapter did not exist. Five fixture tests now pass: known SQLite remapping and integration suppression, unknown table rejection, trigger rejection, longest-prefix / boundary mapping with global-state sanitization, and reserved quarantine collision. The main fixture also proves original DB bytes remain unchanged and JSONL is untouched. Tests use synthetic fixtures only; no real user content was inspected.

Command: `C:\Users\90090\.dotnet\dotnet.exe test tests/CodexBackup.Tests --no-restore --filter FullyQualifiedName~CoreAdapterTests`.

Final amendments: custom CODEX_HOME directories are recognized by Core kind and top-level state/session shape. Mapping inputs must normalize to fully qualified local paths; duplicate normalized sources or targets fail. Path notes are limited to 500 plus a truncation notice. Databases larger than 2 GiB, more than 100,000 rows per path column, or path values above 32,768 characters fail. Known passive global project associations retain only typed local-projects id/name/rootPaths, string-array project-order, and string-valued thread-workspace-root maps; malformed forms reject instead of silently losing associations. Root paths remap; embedded unknown project settings do not activate. Eight adapter fixture tests pass after amendments.

Limitations: this enables known local history reconstruction, not installed application migration, credentials portability, automatic integration activation, or verification that the destination Codex version accepts every retained historical field. UI compatibility must be assessed separately. Unknown column semantics beyond explicitly edited path fields are not guessed; caller should expose version/schema compatibility limitations to the user. The raw top-level thread_history_1.sqlite remains allowed based on its known history purpose, without an independent schema adapter; compatibility or future active semantics cannot be guaranteed. Memories and session files remain passive content by convention. SQLite operation duration is governed by cancellation between API calls and SQLite's connection timeout; no native instruction-budget callback is installed. The adapter returns notes; RestoreEngine owns installation and rollback sequencing.
